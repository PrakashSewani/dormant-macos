# Workflow

- Commit work at phase/milestone boundaries before handing off — starts new sessions from a clean, committed state. Confidence: 0.85
- Validate completed phases (fresh session / independent verification) before starting the next phase — gate progression on validation (user asks "are we done with phase N? can we move on?" and expects a validated yes before proceeding). Same at session scope: asks "are we done with the items that were planned for this session?" and expects a checklist-style wrap-up that ticks planned items and honestly separates open loops (agent's own, e.g. uncommitted work) from the user's manual/human-only tasks. Confidence: 0.92
- Branching standard (user-set, applied across repos): `dev` is the default work branch — all changes land via work-branch → PR → `dev`; `main` is the release branch (release tags cut from `main` only, full/release CI runs there); a green PR build is the merge gate into `dev`, while PRs otherwise just run the check command. Confidence: 0.9
- Hands off routine git landing with a terse imperative ("push code raise pr against dev") and expects the agent to run the whole sequence itself — commit (feature work and taste notes as separate commits), push, open the PR against `dev` — and to settle small landing calls on its own (e.g. bundling a pending commit into one PR) instead of answering an earlier "one PR or split?" question. Confidence: 0.7
- When the user proposes a workflow convention ("let's make a standard"), treat it as durable: record it as a numbered decision doc, wire CI/tooling to match, and update procedure docs — not just follow it verbally for the session. Confidence: 0.75
at survives — as explicit decisions for the human before implementation, with a recommended option; the user answers promptly, accepts well-reasoned recommendations, and wants the outcome recorded as a numbered decision. Confidence: 0.7
- In destructive-operation trade-offs, prefers maximum data safety over aggressive reclamation: stricter deletion scoping (never risk hand-made files/folders sharing a regenerable name) and no lingering duplicate copies of source (e.g. delete archives after a checksum-verified restore) — and wants the exact file disposition spelled out when he asks ("are you zipping the binaries or deleting them"): what is deleted, what is compressed, what is kept. Confidence: 0.7
- Pings mid-task during long background work ("u stuck?") and expects a brief status snapshot (what's done, what's still running) before the wait continues — keep him informed rather than going silent. Confidence: 0.6
- Resumes interrupted/dropped sessions with a bare "pls continue" and expects the agent to pick up exactly at the last pending step (verify that step's result, then continue) — no restart, no long recap. Confidence: 0.6
- Do NOT delegate implementation work to subagents ("do not delegate to subagents you are getting stuck please follow tasks sequencially do it yourself") — do the work directly, sequentially, task by task. Explicitly stated after subagents stalled; applies to implementation especially. Confidence: 0.95
- Project repos are scaffolded from a shared upstream template repo the user maintains and evolves (e.g. `template-app-plus-site`); when he says the template changed, fetch it, diff against the seed commit, and merge ("compare and take the pull") — take untouched files wholesale but preserve local customizations (product name, learned preferences, filled-in real commands) instead of blindly overwriting, and record pulled behaviors as numbered decisions. Confidence: 0.8
- Wants macOS apps distributed via Homebrew — raises it unprompted ("can we publish the app via homebrew? is it compatible?") and cares whether the app actually fits Homebrew's current publishing rules before committing to a path. Resolved it in favor of a free own tap (`brew tap <user>/tap`) over the paid Apple Developer Program + `homebrew/cask` route. Confidence: 0.75
- Kicks off sessions by naming a small explicit item list ("lets keep two items for this session") and expects the session to stick to and wrap up exactly those items. Confidence: 0.7
- For design/creative work, wants many candidate alternatives up front ("create multiple examples… give many examples") delivered as concrete rendered previews (product images, mockups, size ladders) rather than one take or verbal descriptions — then he picks the winner. Confidence: 0.8
- Cares how his public repos read to outsiders: treats embarrassing or off-tone commit messages as "a bad decision" that must be scrubbed — keep commit messages, PR bodies, and public docs neutral and professional (no political/cultural references, even accidental), and when something bad is already pushed, is open to history rewrite + force-push (with the blast radius explained first). Confidence: 0.8
- Periodically asks for an honest audit ("do the docs match the implementation? are the branches in line?") and wants a candid answer that admits gaps, then fixes the drift on the spot (e.g. README left as template boilerplate, docs still describing placeholders after the real code landed) — reconcile docs and branch state with reality before claiming things are done. Confidence: 0.75
- Probes session state with ultra-terse one-liners ("pending items?") and expects the agent to self-locate the state (status docs, task lists) and reply with a compact pending list partitioned by owner — his manual/human-only tasks, the agent's remaining work, and deferred "later" items — with no follow-up questions and no long recap. Confidence: 0.7
- Keeps the promo site's feature copy in sync with shipped features — after a batch of features lands he asks for the site to be updated to describe them ("update site, add info on new featres") and expects stale copy corrected along the way (e.g. "Open in your configured editor" → Open in VS Code), new feature sections to reuse the existing site's look (no ad-hoc CSS), the full check (site build included) run, and the commit pushed onto the open feature PR. Confidence: 0.65
- Reports breakage as a bare statement ("conflicts with dev") and expects the agent to diagnose and repair end-to-end without check-ins — fetch and inspect the divergence, merge `dev` into the feature branch (merge, not rebase), resolve the conflicts, re-run the full check, push, and confirm GitHub sees the PR as mergeable again before reporting back. Confidence: 0.75
- When resolving merge conflicts in the tracker docs (`docs/decisions.md`, `docs/status.md`), keeps the current session's substantive text over the merged-in side: preserve the newer numbered decisions and rewrite the status handoff to the current landing reality instead of reverting to the older snapshot. Confidence: 0.6
